# ADR 002 — Share the contract and behaviors, not a runtime

Status: accepted for the architecture spike.

## Decision

The common layer consists of a **documented JSON contract**, canonical JSON fixtures (including malformed cases), and observable behavioral specifications. Each IDE owns a small native parser/validator and a thin adapter to its own process, path, settings, diagnostic, editor and navigation APIs. No shared executable library, LSP server, metric engine or UI framework is introduced for P2–P8.

The contract records `members[]`, exact field names/types, nullable values, relative-path and 1-based-line semantics, ordering limitations, and the current absence of a version field. The behavior specification records outcomes that all adapters should match: valid exit `0`/`2` reports, failed exit `1`, null-score handling, strict `> 8.0` findings, unusable locations, path containment, and empty analysis. Fixtures are generated or checked against the external CLI, then copied as stable test data. They are not generated by an IDE implementation.

## Platform boundary

| Shared semantics | Platform-specific mechanism |
| --- | --- |
| JSON field meanings and compatibility rules | TypeScript, JVM or .NET parser implementation |
| CRAP value and existing gate supplied by the CLI | VS Code Diagnostics/CodeLens, Rider inspection/editor UI, Visual Studio editor/error surfaces |
| Invocation outcome categories | Process spawning, cancellation, settings and notifications in each host |
| Relative paths and 1-based lines | URI/path handling and zero-based editor coordinates in each host |
| Canonical fixtures and behavioral tests | Test harness and packaging for each SDK |

The VS Code/Cursor adapter may share **its own** TypeScript modules internally among its command, runner, parser, snapshot, diagnostics and CodeLens components. That is ordinary reuse within one product, not a cross-IDE library. Rider may need an IntelliJ front end and a ReSharper back end for certain editor features; that future split is local to its adapter. Visual Studio will select its own extensibility model when implementation begins.

## Alternatives considered

- A shared .NET library favors Visual Studio but is unusable directly in the Node.js extension and may not fit Rider's UI side.
- A shared TypeScript library favors VS Code and does not remove JVM/.NET integration work.
- A language server could standardize presentation only if several IDEs needed the same long-lived language service. The MVP is a manual external analysis with sparse line locations, so LSP adds process and lifecycle complexity without eliminating the CLI boundary.
- Duplicating metric calculations in adapters would contradict `crap4csharp` as the source of truth.

## Consequences

Each adapter writes a small amount of parsing and mapping code, tested against the same fixtures. This is intentional. No adapter may interpret `null` as zero coverage or recalculate CRAP. Schema/behavior changes are reviewed centrally and exercised across all existing adapters. A shared executable can be reconsidered only after concrete repeated implementation and compatible host runtimes are demonstrated. JetBrains' [Rider plugin architecture](https://plugins.jetbrains.com/docs/intellij/rider.html) and Microsoft's [Visual Studio extensibility overview](https://learn.microsoft.com/en-us/visualstudio/extensibility/index) confirm that preserving a data boundary is safer than imposing a common runtime before either plugin exists.
